# 项目流程规范

> 本文整理自 [`docs/solo-ai-software-development-process.md`](../solo-ai-software-development-process.md)，聚焦**人侧**的项目管理、迭代管理与软件管理流程，暂不涉及 AI 角色分工与 Agent 协议。
>
> 适用对象：项目负责人、架构决策者与协作者。

---

## 1. 总体原则

### 1.1 核心思想

> **人负责方向、取舍和最终决策；执行层按规范交付。**

### 1.2 设计原则

- 保留敏捷中的愿景、路线图、版本、迭代、复盘、版本管理等概念
- 避免过重流程和文档负担 → **Minimum Viable Process（最小可行流程）**
- 每个需求至少回答 5 个问题：**Why / What / Acceptance Criteria / How / Done**

### 1.3 两条红线

1. **不要让敏捷变成文档地狱** — 若每天花大量时间写计划/报告/纪要而几乎不推进交付，则本末倒置
2. **人不可放弃方向与关键决策** — 产品方向、关键架构、最终 Approve/Reject 必须由人负责

## 2. 层级体系

### 2.1 六层结构

从战略到代码，建议用以下层级组织工作：

```text
Product Vision（产品愿景）
    ↓
Product Roadmap（路线图）
    ↓
Release / Version（发布版本）
    ↓
Iteration（迭代周期）
    ↓
Epic / Feature → Story → Task / Subtask
    ↓
Git Commit（代码变更）
```

贯穿全生命周期的横切线：

```text
Decision Log / ADR（架构决策记录）
```

### 2.2 概念区分

| 概念 | 含义 | 示例 |
|------|------|------|
| Release / Product Version | 产品交付版本 | v0.1 MVP、v1.0 |
| Iteration | 开发节奏 | 一周一个 Sprint |
| Git Version / Commit | 代码历史状态 | commit、PR |
| Feature / Story / Task | 需求与执行粒度 | 用户故事、工程任务 |

### 2.3 数量关系

```text
1 个 Release  →  多个 Iteration
1 个 Iteration  →  多个 Story
1 个 Story  →  多个 Task
1 个 Task  →  多个 Git Commit
```

## 3. 项目管理

### 3.1 产品发现（Product Discovery）

**Product Vision** — 写代码前先明确：

- 我在做什么？
- 解决什么问题？
- 为谁解决？
- 提供什么价值？
- 大致采用什么方案？

建议用简短 Markdown 记录：Problem / Target User / Solution / Value。

### 3.2 Product Backlog（产品待办）

所有可能的想法进入 Backlog，按状态分组：

```text
Ideas → Planned → In Progress → Done
```

**关键原则：**

> Backlog 是「所有可能做的事情」，不是「我一定要做的事情」。

Backlog 负责**收集与筛选**；Roadmap 和 Release Plan 负责**承诺与排期**。

### 3.3 Product Roadmap（路线图）

描述**未来方向**，不细化到具体 Task。

Roadmap 应表达：

```text
方向 → 能力 → 版本
```

而不是：

```text
写 LoginController / 修改 UserRepository / 修复 JWT bug
```

示例结构：按季度或版本列出能力包（如 v0.1 MVP 含登录、Project、Task 等）。

### 3.4 Release Planning（发布规划）

每个 Release 需有：

1. **明确目标（Release Goal）** — 用户能完成什么
2. **Epic 列表** — 该版本要交付的大能力块

示例：

```text
v0.1 MVP

Release Goal:
  用户能够创建项目并完成核心交易复盘流程。

Epic:
  Epic 1 — 行情数据管理
  Epic 2 — 图表与指标
  Epic 3 — 本地 Python 数据处理
```

### 3.5 需求拆解：Epic → Story → Task

| 层级 | 粒度 | 关注点 |
|------|------|--------|
| **Epic** | 较大产品能力 | 如「用户认证」「图表布局」 |
| **Story** | 用户价值与行为 | 「作为…我希望…从而…」 |
| **Acceptance Criteria** | 验收标准 | Given / When / Then |
| **Task** | 工程任务 | 数据模型、API、UI、测试、Review 等 |

Story 从**用户价值**出发；Task 从**工程实现**出发。

**Acceptance Criteria 示例：**

```text
Given 用户已打开图表页面

When 用户添加 MA 指标

Then 图表应显示对应周期的 MA 线，且 legend 标签正确。
```

### 3.6 优先级管理

**Bug 优先级（P0–P4）：**

```text
P0 — 系统不可用
P1 — 主要功能损坏
P2 — 重要缺陷
P3 — 次要缺陷
P4 — 锦上添花
```

**功能优先级（MoSCoW）：**

```text
Must / Should / Could / Won't
```

### 3.7 Bug 管理流程

不要「发现 bug → 直接改」，应走固定流程：

```text
Bug → Report → Triage → Priority → Root Cause Analysis
    → Fix → Regression Test → Review → Done
```

Bug 记录至少包含：

- Expected / Actual Behavior
- Reproduction Steps
- Environment
- Severity / Priority
- Root Cause / Fix / Regression Test

### 3.8 完整产品闭环

```text
PRODUCT VISION
    ↓
ROADMAP
    ↓
RELEASE
    ↓
BACKLOG
    ↓
ITERATION PLAN
    ↓
STORY → TASK
    ↓
实现 → 测试 → 审查 → 合并
    ↓
RELEASE
    ↓
RETROSPECTIVE
    ↓
PROCESS IMPROVEMENT → 回到 BACKLOG
```

## 4. 迭代管理

### 4.1 Iteration 节奏

建议：**1 周一个 Iteration**（单人项目可灵活，但需有固定节奏）。

每个 Iteration 示例结构：

```text
Iteration 2026-W36（Sprint11）

Goal: 完成自定义 Python 脚本 MVP

Planned:
  US-001 脚本编辑器
  US-002 脚本执行与图表渲染
  US-003 脚本持久化
```

### 4.2 Iteration 启动清单

1. 查看 Product Backlog
2. 确定本周目标
3. 选择 Story
4. 拆 Task
5. 估算工作量
6. 开始执行

### 4.3 Definition of Ready（DoR）— 开工门槛

Story / Task **未满足 DoR 不允许进入开发**：

```text
□ 目标明确
□ 背景明确
□ Acceptance Criteria 明确
□ Dependencies 明确
□ 技术约束明确
□ 输入资料存在
□ 没有明显阻塞
```

### 4.4 Definition of Done（DoD）— 完成门槛

「写完了」≠ Done。完成检查项：

```text
□ 实现完成
□ 单元测试通过
□ 集成测试通过
□ Lint 通过
□ 构建通过
□ 安全检查
□ 文档已更新
□ Acceptance Criteria 满足
□ Code Review 完成
□ Git 已提交
□ 已合并
```

### 4.5 Task 生命周期

正常流转：

```text
BACKLOG → READY → ANALYZING → DESIGNING → IMPLEMENTING
       → TESTING → REVIEWING → DONE
```

异常状态：`BLOCKED` / `CANCELLED`

每个 Task 应有明确的 **Input / Output**：

```yaml
id: TASK-123
title: 实现用户登录

objective:
  允许用户使用邮箱/密码登录。

input:
  - 产品需求
  - API 规格
  - 数据库 schema

constraints:
  - TypeScript
  - SQLite
  - Electron IPC

expected_output:
  - 实现代码
  - 单元测试
  - 集成测试
  - 文档更新

acceptance_criteria:
  - 合法用户可登录
  - 错误密码被拒绝
  - 未激活用户被拒绝
```

### 4.6 度量：Cycle Time 优于 Story Points

单人场景下 Story Points 价值有限，更应关注：

```text
Cycle Time = Task 从开始到 Done 的耗时
```

可长期统计：

- 平均 Task Cycle Time
- 实现时间 / Review 时间 / Rework 时间
- Bug Rate

### 4.7 Daily Log（日终记录，约 5 分钟）

不必模拟传统 Daily Standup，建议每天结束记录：

```markdown
# 2026-08-29

## Completed
- TASK-101
- TASK-102

## In Progress
- TASK-103

## Blocked
- 第三方 API 凭证未配置

## Decisions
- 选用 SQLite 作为业务库

## Problems
- 集成测试不稳定

## Tomorrow
- 修复集成测试
- 启动 TASK-104
```

### 4.8 Retrospective（迭代复盘）

每个 Iteration 结束后回答：

```text
What went well?
What went wrong?
What should change?
What should we automate?
```

产出 **Process Improvement**（如：Task 太大 → 控制在半天工作量以内），并反馈到 Backlog。

## 5. 软件管理

### 5.1 Git 作为底层追踪链

项目管理与代码通过 Git 串联：

```text
Project Management → Task → Branch → Commit → PR → Review → Merge
```

完整追踪链：

```text
Release → Story → Task → PR → Commit → Code
```

示例：

```text
TASK-123 → feature/TASK-123-user-login → commit → PR #42 → Review → Merge
```

### 5.2 Git Commit 规范

```text
feat(auth): add user login
fix(auth): handle expired token
test(auth): add login integration tests
refactor(auth): extract token service
docs(auth): update authentication spec
```

可附带 Task ID：

```text
feat(auth): add user login [TASK-123]
```

**分支规则：** 禁止直接 commit 到 main；通过 PR 合并。

### 5.3 文档与知识管理

建议目录结构，防止设计与决策随时间漂移：

```text
docs/
├── project-rules/          # 项目流程与工程规范（本文档所在目录）
├── solo-ai-software-development-process.md
├── releases/
│   └── v0.1/
│       ├── trading-zone-electron架构文档.md
│       └── SprintN/        # 各迭代启动文档、迭代文档、问题纪要
├── product/                # 愿景、路线图（可选扩展）
├── requirements/           # 用户故事（可选扩展）
├── architecture/           # 架构概览（可选扩展）
├── decisions/              # ADR（可选扩展）
├── development/            # 开发约定、测试规范（可选扩展）
└── operations/             # 部署、监控（可选扩展）
```

**ADR（Architecture Decision Record）** 贯穿全生命周期，记录关键架构与产品决策。

公开行为变更时必须同步更新文档。

### 5.4 项目开发规范

项目级工程规范（如 `AGENTS.md` 或本目录下的其他规范文件）应涵盖：

- 架构原则
- 语言、数据库、API 风格
- 测试要求
- Git 规则
- 文档与安全规范

### 5.5 版本化原则

**Requirement / Architecture / Decision / Task / Code / Test / Release 全部进 Git**，形成可追溯历史。

## 6. 与本项目的映射

当前 `trading-zone-electron` 已有实践与上述体系的对应关系：

| 规范概念 | 本项目对应 |
|----------|-----------|
| Product Vision / Roadmap | 顶层产品目标、架构文档 |
| Release | `docs/releases/v0.1/` |
| Iteration | `SprintN` 启动文档 + 迭代文档 |
| Story / Task | 迭代文档内的需求与任务拆解 |
| ADR | 架构决策纪要（如 Sprint8 中期架构梳理） |
| Retrospective | 迭代文档中的「改进项 / 问题纪要」 |
| Backlog | Ideas + Planned 待办池 |

迭代文档建议遵循固定结构（目标、需求、设计、任务、测试结果、改进项），详见 `.cursor/skills/sprint-iteration-doc/SKILL.md`。

## 7. 落地阶段

### Phase 1：最小流程

```text
Product → Release → Iteration → Story → Task → Git
+ Definition of Done
```

### Phase 2：工程治理

```text
Architecture / ADR / Testing / CI/CD / Security
Documentation / Git conventions
```

### Phase 3：度量与持续改进

```text
Cycle Time / Lead Time / Rework Rate / Bug Rate
Review Time / Release Frequency
→ 通过 Retrospective 持续优化
```

## 8. 最小需求五问

任何新需求开工前，至少回答：

```text
Why?                  — 为什么做？
What?                 — 做什么？
Acceptance Criteria?  — 什么叫完成？
How?                  — 准备怎么做？
Done?                 — 什么条件下可以关闭？
```
