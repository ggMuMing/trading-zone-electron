- v0.1版本实现了图表和自研脚本的基础互动，可以遵循脚本语法创建主图MA指标和副图MACD指标，并在前端UI显示

  - 和UI的交互耦合严重；

- UI功能方面。可以和自定义的脚本正确交互；至少实现通达信/东财相同的可视化界面的正确显示和增删改查功能
- 调研pine中可编程化的图表展示的实现方法

# 2.Backlog

### 一、产品模型——商流链模型

- a.Script系统——货源/原材料开采商
- b.Protocol系统——货场/加工供应链
- c.UI Controller系统——渠道商/客场
- d.Chart系统——消费者

概念定义：

- 元数据——Script系统“开采”输出的原材料
- 图表数据——消费者消费的产品

#### a.Script系统

> 提供“开采”元数据——ohlcv+算法、“定制化开采”——创建指标功能。

- `自研Script框架`
  - 框架内包含一个功能集合，这个集合：
    - 既可以服务于内置算法（例如内置MA、内置MACD）
    - 也可以服务于定制化算法（自定义KDJ、RSI）
- 产品一：“开采”元数据——ohlcv+算法
  - 接口：消费者可以下单要求提供ohlcv数据和算法计算后的指标数据
  - ohlcv：“矿石”，最基础的功能。
  - 内置算法：进阶功能。基于`自研Script框架`自研。
  - 定制算法：定制功能。基于`自研Script框架`定制。
- 产品二：“定制化开采”——创建指标功能
  - 接口：消费者可以根据`自研Script框架`指南，创建需求单——脚本，交给Script系统
- “开采”出来的数据，可以直接交给`Protocol系统`加工
- 自研Script框架在系统内部，不需要“仓库”存储
- 内置算法、定制算法需要“仓库”存储



#### b.Protocol系统

> Protocol系统名字取自网络通信协议——网络通信双方的数据遵循协议才能实现通信。在商流链中，它是供应链的一环，链接原材料和下游需求。

- 功能：接收上游原材料，生产下游需要的产品
  - 接收上游原材料：和上游`Script系统`达成协议——以什么样子交付原材料
  - 生产出下游需要的产品：和下游消费者的需求达成协议——这里对接的是渠道商，渠道商的需求就是终端消费者的需求
  - 如果上游能提供的产品增加了（自研Script框架边界扩大），下游的需求相应也增加了（根据自研Script框架扩大而衍生的需求），Protocol系统需要自己进化，改进加工环节。
    - Script系统环节中的定制化需求和获取数据都是Script系统提供的接口，消费者想消费只需要遵循`自研Script框架`的边界和接口自行决定是否“下单”，这里消费者和生产环节解耦
    - Protocol环节是上下游真正耦合的地方。它既需要知道生产环节的输出还需要消费者的需求形态。
  - 后续畅想：原材料源和供应链生产环节是否可以合并？
    - Script系统是否有必要自行掌握Protocol系统？
    - Script系统是否可以自行掌握Protocol系统？



#### UI Controller系统

> UI Controller系统扮演了渠道商和客场的角色。它为消费者提供了消费的场所，消费者只能在它这里下单。消费者也不需要考虑产品（数据）的初期处理和中间传输环节。

- UI Controller系统知道Script系统和Protocol系统最终的产出，以此为客户提供市面上能买到的`图表数据`清单。消费者向它下单，它再向Script系统和Protocol系统下单“原材料采集”和“产品加工”
- UI Controller系统还为消费提供这样的服务：它替消费者向Script系统下单`创建定制化需求`



#### Chart系统

> Chart系统是终端消费者，它服务于应用的使用者。它只需要维护Lightweight-charts需要的数据，并向UI Controller下单获取这些数据



#### 补充

- 所有数据都遵循时间序列
