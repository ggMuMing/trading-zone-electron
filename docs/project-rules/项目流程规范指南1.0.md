# 1.版本管理

## 1.1 版本组成

```text
Release → Iteration → Story -> Task → Git Commit
```

**Release**

- 首字母`v`用小写
- v1.1.2 每一位数字的含义
  - `1.x`：正式版本：完整功能修改
  - `x.1.x`：中期版本：功能模块修改
  - `x.x.1`：短期迭代版本：短期功能修改
- release目录管理的最小颗粒为中期版本
  - 合理目录：`v1.1`、`v2.3`、`v5.0`
  - 错误目录：`v1`(大版本)、`v1.2.1`(迭代版本)
- 大版本发布版本格式：`vX.0`

**Iteration**

- 应体现在realease号的最小版本里面，例如：v1.1.**2**

**Stroy**

- 使用`US+数字`，例如：`US1`、`US2`

**Task**

- 使用`小写task+数字`，例如：`task1`、`task2`

**Git Commit**:

- commit的时候，带入整个任务的版本链条作为编码
  - `TZE-v1.1.2-1-2`：项目缩写-release-UserStory-task

## 1.2 Git 远程分支

### Branch 与 Tag 的分工


| 类型             | 作用                     | 生命周期              |
| -------------- | ---------------------- | ----------------- |
| **Branch（分支）** | 承载正在进行的开发              | 长期分支永久保留；迭代分支临时存在 |
| **Tag（标签）**    | 标记某次 Iteration 完成的代码快照 | 永久保留，不可移动         |


> **Branch 流动，Tag 定格。** 迭代分支 merge 后删除，由 Tag 承担历史回溯。



### 远程分支分类

**长期分支（Remote，永久保留）**


| 类型   | 命名示例          | 说明                                          |
| ---- | ------------- | ------------------------------------------- |
| 大版本  | `v1.0`、`v2.0` | 对应 semver 首位 `X.0`，标志完整产品代际                 |
| 中期版本 | `v1.1`、`v2.3` | 对应 semver 中位，与 `docs/releases/v1.1/` 目录粒度一致 |


**临时分支（Remote，Iteration 期间存在）**


| 类型   | 命名示例              | 说明                                    |
| ---- | ----------------- | ------------------------------------- |
| 迭代版本 | `v1.1.1`、`v2.3.1` | 对应 semver 末位，一个 Sprint / Iteration 一条 |


命名与版本号对应关系：

```text
v1.1.2
 │ │ └── 迭代分支 v1.1.2（临时）
 │ └──── 中期分支 v1.1（长期）
 └────── 大版本分支 v1.0（长期）
```



### Iteration 工作流

每个 Iteration 按以下流程操作远程分支：

```text
1. 从中期分支拉迭代分支
   v1.1  →  v1.1.1

2. 在 v1.1.1 上开发、提交
   commit message: TZE-v1.1.1-US1-task2 ...

3. Iteration 验收通过，合并到中期分支
   v1.1.1  →  merge  →  v1.1

4. 在 merge 后的 commit 上打 Tag
   tag: v1.1.1

5. 删除临时迭代分支（本地 + 远程）
   delete v1.1.1
```

示意：

```text
v1.0 ─────────────────────────────────────────→（大版本，长期）
  │
v1.1 ──────────●────────────●────────────●────→（中期版本，长期）
               ↑ merge     ↑ merge
v1.1.1 ───●────┘           │              （迭代，临时，merge 后删除）
          tag v1.1.1       │
v1.1.2 ───────────●────────┘
                  tag v1.1.2
```



### Tag 规则

- **命名**：与 Iteration 版本号一致，如 `v1.1.1`、`v2.3.2`
- **时机**：Iteration merge 进中期分支后立即打 Tag
- **用途**：标记该 Iteration 的交付快照；日后回溯、hotfix 均从 Tag 拉出
- **禁止**：Tag 一旦创建不可移动；需修正时打新 Tag（如 `v1.1.2`），不在原 Tag 上覆盖



### 分支与 docs 目录的对应


| Git          | 文档目录                                  |
| ------------ | ------------------------------------- |
| 中期分支 `v1.1`  | `docs/releases/v1.1/`                 |
| Tag `v1.1.2` | 该 Iteration 的 Sprint 文档（如 `Sprint2/`） |
| 大版本分支 `v1.0` | 跨中期的产品级里程碑文档（可选）                      |




### 禁止事项

- 禁止向大版本 / 中期长期分支直接 push 未经验收的 commit（应经迭代分支 merge）
- 禁止在 Tag 上继续提交（需修改时从 Tag 拉 hotfix 分支）
- 禁止迭代分支 merge 后保留不删（避免与 Tag 职责重叠）



# 2.项目文档

设计原则：

- 保留敏捷中的愿景、路线图、版本、迭代、复盘、版本管理等概念
- 避免过重流程和文档负担 → Minimum Viable Process（最小可行流程）
- 每个需求至少回答 5 个问题：Why / What / Acceptance Criteria / How / Done



## 2.1 产品发现/产品愿景（Product Discovery）

- 我在做什么？
- 解决什么问题？
- 为谁解决？
- 提供什么价值？
- 大致采用什么方案？
- 用简短 Markdown 记录：Problem / Target User / Solution / Value



## 2.2 Product Backlog（产品待办）

所有可能的想法进入 Backlog，按状态分组：

```text
Ideas → Planned → In Progress → Done
```

**关键原则：**

> Backlog 是「所有可能做的事情」，不是「我一定要做的事情」。

- Backlog 负责**收集与筛选**；
- Roadmap 和 Release Plan 负责**承诺与排期**。



## 2.3 Product Roadmap（路线图）

描述**未来方向**，不细化到具体 Task。

Roadmap 应表达：

```text
方向 → 能力 → 版本
```

而不是：

```text
写 LoginController / 修改 UserRepository / 修复 JWT bug
```

示例结构：按季度或版本列出能力包（如 v0.1 MVP 含登录、Project、Task 等）。

## 2.4 Release Planning（发布规划）

每个 Release 需有：

1. **明确目标（Release Goal）** — 用户能完成什么
2. **Epic 列表** — 该版本要交付的大能力块
示例：

```text
v0.1 MVP

Release Goal:
  用户能够创建项目并完成核心交易复盘流程。

Epic:
  Epic 1 — 行情数据管理
  Epic 2 — 图表与指标
  Epic 3 — 本地 Python 数据处理
```

## 2.5 需求拆解：Epic → Story → Task

| 层级 | 粒度 | 关注点 |
|------|------|--------|
| **Epic** | 较大产品能力 | 如「用户认证」「图表布局」 |
| **Story** | 用户价值与行为 | 「作为…我希望…从而…」 |
| **Acceptance Criteria** | 验收标准 | Given / When / Then |
| **Task** | 工程任务 | 数据模型、API、UI、测试、Review 等 |

Story 从**用户价值**出发；Task 从**工程实现**出发。

**Acceptance Criteria 示例：**

```text
Given 用户已打开图表页面

When 用户添加 MA 指标

Then 图表应显示对应周期的 MA 线，且 legend 标签正确。
```

## 2.6 优先级管理

**Bug 优先级（P0–P4）：**

```text
P0 — 系统不可用
P1 — 主要功能损坏
P2 — 重要缺陷
P3 — 次要缺陷
P4 — 锦上添花
```

**功能优先级（MoSCoW）：**

```text
Must / Should / Could / Won't
```

## 2.7 Bug 管理流程

不要「发现 bug → 直接改」，应走固定流程：

```text
Bug → Report → Triage → Priority → Root Cause Analysis
    → Fix → Regression Test → Review → Done
```

Bug 记录至少包含：

- Expected / Actual Behavior
- Reproduction Steps
- Environment
- Severity / Priority
- Root Cause / Fix / Regression Test


## 2.8 完整产品闭环

```text
PRODUCT VISION
    ↓
ROADMAP
    ↓
RELEASE
    ↓
BACKLOG
    ↓
ITERATION PLAN
    ↓
STORY → TASK
    ↓
实现 → 测试 → 审查 → 合并
    ↓
RELEASE
    ↓
RETROSPECTIVE
    ↓
PROCESS IMPROVEMENT → 回到 BACKLOG
```
